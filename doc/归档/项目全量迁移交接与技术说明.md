## 0. 一页读懂

Autodidact 要做的不是“会聊天的网页”，也不是“把搜索结果塞给模型的普通 RAG”。它是一个长期存在的研究型学习器：自己选择目标，检索和阅读资料，形成可追溯的主张，对照已有信念，处理冲突，考试、反思，再留下下一轮学习目标。当前大模型只是可替换的推理工具；真正要保留下来的是目标、来源、证据、信念、争议、历史、评估和技能。

当前代码能跑一个**原型级**学习循环，具有数据库迁移、搜索回退、来源去重、Claim 原文锚点及语义支持判定、信念晋升门槛、争议四结果服务和可降级的 pgvector 信念召回。但“真正闭卷考试”“自动完成争议调查”“网页聊天界面”“模型迁移实验”“30 天无人值守验证”尚未完成。不要把设计稿或数据表的存在误当成功能已上线。

本轮交接的最重要下一步是：在专用 PostgreSQL/pgvector 测试库完成在线验收，然后补齐真正隔离的闭卷评估和安全的端到端运行验证。未完成在线测试之前，不能宣称数据库迁移和并发写入已在真实数据库上通过。

## 3. 最初方案的“灵魂”：为什么这样设计

### 3.1 模型不是智能体

最初设想不是让模型不停训练参数，也不是让模型一次回答更多文字。V0.1 主要学习前三层：知识、经验、程序性技能；模型参数训练属于以后再考虑的第四层。长期身份由使命、目标、记忆、证据、信念、争议、技能和评估历史组成。因此更换推理模型不等于更换智能体。

一个便于理解的类比：LLM 是“可换的研究员”，数据库和控制逻辑是“研究机构的档案、规程和判断记录”。研究员的意见能提出新的调查线索，不能把档案中已有的高置信结论直接改掉。

### 3.2 信息、主张和信念必须分开

```text
网页/论文/模型回答（原材料；模型回答初始证据等级 0）
    → Source / ModelObservation（保存出处与原文）
    → Claim（可检查的候选命题）
    → ClaimEvidence / Evidence（哪段原文支持、反驳或限定它）
    → 评估 + 与旧信念比较
    → Belief（目前接受的结论）或 Dispute（待调查矛盾）
    → BeliefHistory（结论为什么改变）
```

记忆可以说“我读过什么”；信念要回答“我现在相信什么，以及凭什么”。网页摘录真的存在，只能证明“引用没有凭空捏造”，不能自动证明摘录支持完整主张。多个相同网站的转载也不能算多个独立证据。

### 3.3 真正学习应接受考试，而不是自我感觉良好

早期方案要求“生成问题→闭卷回答→重新查来源→评分→反思→复测”，并另测迁移、保持度和校准度。它提出 Day 0/7/14/21/30 冻结基准，在“同一个模型单独回答”和“同一个模型使用智能体记忆”两组条件下比较，才能识别积累记忆是否真的带来能力增益。原稿中诸如“Day 30 提升 20%”“自主目标占比超过 70%”是**实验成功判据/目标值**，不是目前结果。

### 3.4 争议是学习机会，不是覆盖操作

高置信旧信念与新主张冲突时，先创建 `Dispute`，保存旧状态，收集双方独立证据并核对范围和条件，最后可能保留旧结论、采用新结论、形成条件化结论，或继续未解决。例如“IMU 在短时视觉失效时能辅助估计”与“长期缺乏视觉约束会漂移”并不一定互相排斥；调查可能产出更精确的条件化知识。

### 3.5 长期愿景，不等于当下能力

原稿还设计四类记忆（工作、情节、语义、程序）、知识图谱、元记忆与 Mastery Profile、每日整合和技能提取、多模型独立咨询、模型能力地图与路由器，以及 V0.2 的学习策略 A/B 测试。这些是设计方向；当前仓库并未完整实现对应的独立子系统。原稿建议的庞大目录也仅是建议，不应为凑目录而提前建空模块。

### 3.6 原始方案中值得保留的具体设计参数

这些是**当初讨论的候选设计和验收目标**，不是已运行结果；落实时仍需通过实验调整。

- **研究领域与起点：**先聚焦“现代无人机自主系统”，种子问题是“无人机如何知道自己的位置和姿态？”。预期学习路径可由 IMU、GNSS、EKF、VIO 延伸到 Quaternion、坐标变换与 SO(3) 等前置知识，而不是第一天学习整个互联网。
- **四类记忆：**工作记忆存当前问题和计划，情节记忆存一次尝试和反思，语义记忆存已形成的可修正知识，程序性记忆存重复验证有效的做事方法。早期方案要求每日合并重复主张、检查冲突、复核置信度并提炼技能；低价值内容先归档，不立即删除。
- **目标选择：**原稿给出的参考式是 `0.30×重要度 + 0.25×不确定度 + 0.15×新颖度 + 0.20×未来用途 + 0.10×前置收益 − 0.15×学习成本`，另加探索奖励，并建议大致 70% 利用、30% 探索。当前 `goal_score` 采用相近加权式，但不等于完整的 70/30 调度器。
- **评估：**最初建议事实性、推理、迁移、完整性、校准度分别约占 35%、25%、20%、10%、10%；并提出约 0.82 的高质量通过阈值。权重和阈值必须在闭卷/独立核源的实现与数据集上重新验证，不能用同一模型的自评分当作能力证据。
- **每日节奏：**早期构想是白天生成 5—10 个目标、学习与补救，夜间整合记忆并输出日报；这只是未来调度方案。当前 `run --max-cycles N` 只是有上限的循环，不是每天定时任务。
- **模型迁移：**换模型时保持 Agent ID、Belief、Evidence、Goal、Skill 和评估历史不变；冻结题集与数据库，对旧模型/新模型分别测“裸模型”和“加同一份智能体记忆”四组（A1/A2/B1/B2），比较记忆增益。不同意见要进入争议，而不是“新模型自动获胜”。
- **网页模型咨询：**原稿有盲审、找错式批判审查和综合三种模式，并建议重要问题先让多个模型独立回答，再做交叉质询。网页回答及其引用都是线索；必须直接打开被引用的原始资料，核对原文是否支持 Claim。现有 Playwright 适配器还没实现这套完整工作流。
- **30 天实验：**在 Day 0/7/14/21/30 用学习器不可见的冻结题集记录基准分、已验证知识比例、自主目标比例、目标成功率、迁移/保持/校准与高置信错误。原稿设想 Day 30 比 Day 0 至少提高 20%、自主目标比例超过 70%、形成稳定程序性技能；目前都只是目标，不是已测事实。
- **安全边界：**最初就排除了自动修改核心代码、任意 shell、自动登录重要网站、发帖/发消息、删除文件、自动付款、绕过 CAPTCHA 与反爬限制。外部网页和模型输出只可提出主张，不能发出控制命令。

### 3.7 原始方案提出的四个代表性验收场景

1. **首次真实学习：**以无人机定位与姿态为种子，能检索多来源，抽取 IMU/GNSS/EKF/VIO 主张，保存证据、发现矛盾、考试和反思，并产生 Quaternion 等前置目标与完整会话记录。
2. **更换模型：**保留同一个智能体的知识和历史，完成 A1/A2/B1/B2 四组对照；新模型的反对意见不直接改写信念。
3. **网页模型：**至少一个可选适配器，输出落成等级 0 的 `ModelObservation`，引用可追溯，页面失效不令学习器整体停止。
4. **争议调查与 30 天验证：**独立复核新旧双方证据后输出四类决议，并在冻结基准上记录多个时间点的真实能力变化。

当前代码只实现上述场景中的**部分组件**。下一位开发者应把这些场景拆成可运行、可重放、可验收的小步，而不是把原稿里的伪代码当作已经通过的测试。

| `tools/reader.py` | 抓取 HTML/文本、提取正文并作初步质量分类 | 仍缺少充分的内网地址、重定向链和响应大小限制。 |
| `knowledge/claim_support.py` | 核对引用 URL、摘录长度和是否逐字出现在已读原文 | 锚点成立不等于语义支持。 |
| `knowledge/support_assessment.py` | 对完整 Claim 与摘录做支持/反驳/条件/不明确判定，记录理由 | 当前是模型辅助观察，不能宣称形式化证明。 |
| `knowledge/sources.py` | URL 规范化、发布者和内容哈希去重、保守证据等级初筛 | 未完成转载血缘和严格内容质量识别。 |
| `knowledge/promotion.py` | 根据评估、争议、独立来源数与最低等级决定是否晋升 | 无来源不晋升；合格单来源可为临时信念，达门槛才可验证。 |
| `knowledge/conflicts.py`、`disputes.py` | 模型辅助冲突比较；四结果决议政策和调用 | 决议服务已实现，但主循环尚无自主调查队列来形成可信提案。 |
| `embeddings.py` | 可关闭或使用 1536 维 OpenAI-compatible 嵌入 | 召回失败回退最近信念；不是事实裁决。 |
| `models.py`、`repository.py` | SQLAlchemy 表与数据库操作、事务、幂等键 | 迁移和写入应保护已有学习状态。 |
| `learning/evaluator.py` | 当前模型辅助评估和分项结果 | 它把学习结果和来源摘录一起给模型，不是真正闭卷。 |
| `web_models/` | Playwright 通用网页模型适配器原型 | 未接主循环、未统一保存观察；也不是供用户访问的 Web UI。 |
| `benchmark.py`、`metrics.py` | 简单题集评分与基础指标 | 未形成私有冻结集、定期快照或严格校准报告。 |

### 4.2 当前一次 `run-once` 的真实流程

```text
CLI 初始化/升级数据库 → bootstrap 使命与种子目标
→ 目标池为空时由模型提候选目标 → 选最高优先级可运行目标
→ 从现有信念取上下文 → 规划查询
→ 搜索（Brave 可选，DuckDuckGo 后备）→ 读取与去重网页
→ 综合候选 Claim → 原文摘录锚点核验 → 模型辅助语义支持判定
→ Claim + ClaimEvidence 入库 → 语义/最近信念召回 → 比较冲突并创建 Dispute
→ 当前模型辅助 Evaluator → Reflection → 保存 LearningSession 和评估
→ 合格且无争议的 Claim 晋升 Belief、保存 Evidence、尝试写入嵌入
→ 创建前置知识/未答问题/争议调查跟进目标 → 返回本轮统计
```

需要注意三点。第一，`run-once` 是研究学习循环，**不是问答聊天**。第二，调用真实外部 LLM、搜索和数据库前需配置依赖；Mock 模型不会让它真正研究。第三，主循环内许多步骤分别提交数据库，完整循环的崩溃恢复和全程事务边界尚未完成；只有争议决议路径做了单事务加固。

### 4.3 关键对象关系（通俗解释）

| 对象/表 | 一句话用途 |
|---|---|
| `agents` | 保存智能体使命、焦点和运行计数，不与某个模型绑定。 |
| `goals` | 保存想学什么、来自人还是自主生成、优先级与重试状态。 |
| `learning_sessions` | 保存一次学习尝试的计划、结果和反思。 |
| `sources` | 保存读到的原始网页/文本及 URL、发布者、哈希、质量初筛。 |
| `claims` | 保存本轮提出的候选命题，不代表已被接受。 |
| `claim_evidence` | 保存 Claim 引用的具体摘录、锚点哈希、支持关系与理由。 |
| `beliefs` | 保存当前接受程度不同的结论，可附 1536 维嵌入。 |
| `evidence` | 把 Belief 与支持/反驳它的来源连接起来。 |
| `disputes` | 保存新旧结论之间尚需调查或已经决议的冲突。 |

## 5. 证据、争议与数据库的技术细节

### 5.1 从 Claim 到 Belief 的门槛

1. `Synthesizer` 生成 Claim 及所引 URL、原文摘录。
2. `ClaimSupportValidator` 要求 URL 曾被本轮读取、摘录达到最短长度且可在提取正文中逐字找到。
3. `ClaimSupportAssessor` 用模型检查摘录是否支持**整条**命题，区分 `supports`、`contradicts`、`conditional`、`unclear`。提供方故障按 `unclear` 处理。理由和模型名称写入 `claim_evidence`；只有 `supported` 可贡献晋升来源。
4. 同一来源若有支持与反驳/不明确的混合摘录，不作为合格来源。旧记录只写了 `anchored` 的，不会自动被当作语义支持，也不会被静默删除。
5. 通过评估、无未结实质争议、至少有可追溯来源，才允许创建 Belief。多个同发布者或同正文哈希页面只算一个独立证据组；达到配置的独立来源数和最低证据等级才能进入 `VERIFIED`。

边界：语义支持判定当前仍来自 LLM；`supported` 是待复核的观察，不保证科学正确。来源的“官方/教材/普通网页”等等级也多由 URL 和类型规则推断，不是逐篇人工鉴定。避免把这些阈值解释成真理概率。

### 5.2 Dispute 四种结果

| 结果 | 数据层动作 | 必须满足的证据条件 |
|---|---|---|
| `keep_old` 保留旧结论 | 恢复旧信念原状态，争议标记为保留旧结论 | 旧 Belief 对应的支持证据及相同命题的已判支持 Claim 来源，满足独立来源数。 |
| `adopt_new` 采用新结论 | 撤回旧信念，新建受支持的新信念，记录双方历史及 Evidence | 新 Claim 已判支持的独立来源达到门槛。 |
| `conditional` 条件化结论 | 削弱旧信念，新建带条件的新信念 | 条件化表述必须与已获支持且带条件的新 Claim 对齐，且有合格独立来源。 |
| `unresolved` 保持未解决 | 旧信念和争议保持未解决，写入历史 | 不伪称已接受来源；后续可以补充证据再决议。 |

`DisputeResolver` 不直接相信提案列出的来源 ID，而从数据库核查 `ClaimEvidence`、`Evidence` 和来源等级；仓储层在行锁下再次核对独立性，然后将状态、证据、历史和元数据在同一事务提交。相同决议重试幂等，互斥结果不能随意覆盖已终结决议。目前**缺少从调查目标自动收集双边新证据、生成决议提案并调用服务的完整工作流**；服务存在不代表争议会自动解决。

### 5.3 数据库版本与兼容性

| 迁移 | 含义 | 对已有学习状态的影响 |
|---|---|---|
| `20260914_0001` | PostgreSQL/pgvector 初始表结构 | 新库的基线。 |
| `20260915_0002` | 扩展来源 URL、发布者、质量元数据 | 不删除旧记录；为旧来源做保守回填，不把旧来源自动提升为高等级证据。 |
| `20260920_0003` | `claim_evidence`、争议元数据、Claim/Evidence/Dispute 幂等键、部分唯一索引、Belief 向量索引 | 扩展式迁移；旧幂等键不回填，旧 ClaimEvidence 不凭空生成。 |

`autodidact init-db` 走 Alembic。对没有版本表的旧库，程序比较**完整的已知表和字段集合**，仅在严格匹配 0001、0002 或当前结构时才标记并升级；未知/不完整结构会停下，避免错误 stamp 伤及已有状态。最近一轮 Claim 支持和争议加固复用了现有列，**没有新迁移或删除数据**。迁移降级可能删除新增字段及其数据，不应对有价值的学习库随意执行；先备份再操作。

并发写入通过数据库唯一约束与幂等键双层保护；程序只把指定唯一约束的 SQLSTATE 23505 视为可恢复竞争，其它外键/完整性错误会向上报告。当前单元测试覆盖判别逻辑，但真实 asyncpg/pgvector 集成测试仍未执行，不能把“离线通过”写作“线上可靠”。

## 6. 安装、配置与当前使用方式（Windows）

### 6.1 运行形态和部署误区

这是一个 Python 命令行项目；目前没有打包好的 EXE，也没有对普通用户开放的 Web 服务或网页聊天界面。`docker-compose.yml` 只启动本地 PostgreSQL+pgvector，**不是把整个智能体部署到服务器**。开发阶段可以在 Windows 本机运行 Python 和 Docker Desktop；也可连接自行准备的 PostgreSQL/pgvector，数据库不必在 Docker 内。若日后要让别人通过浏览器使用，需要另行设计 HTTP API、前端、身份验证、任务队列和状态展示；不能把 Playwright 网页模型适配器误认成前端。

### 6.2 可重复的本地启动

前提：Python 3.12+、Git、可用的 PostgreSQL 及 `vector` 扩展；以下示例用 Docker Desktop 提供数据库。命令需在仓库根目录运行，真实 `.env` 含密钥，不要提交 Git。

```powershell
Copy-Item .env.example .env
docker compose up -d
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"
.venv\Scripts\python.exe -m playwright install chromium
.venv\Scripts\autodidact.exe init-db
.venv\Scripts\autodidact.exe bootstrap
.venv\Scripts\autodidact.exe run-once
.venv\Scripts\autodidact.exe status
```

`pytest` 是开发依赖。如果系统 Python 或应用内置 Python 提示缺少它，不必污染那个解释器：确认项目 `.venv` 已安装 `.[dev]`，并用 `.venv\Scripts\python.exe -m pytest -q`。历史截图中把 `-version` 写成单横线出现报错，正确命令是 `python --version`；这与项目配置问题不同。

`.env.example` 初始 `LLM_PROVIDER=mock`。Mock 仅供烟测；真实研究需要填写 OpenAI-compatible 聊天端点的 `LLM_PROVIDER`、`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`。搜索 `SEARCH_PROVIDER=auto`：有 Brave 密钥优先 API，故障/空结果回退 DuckDuckGo HTML；无密钥直接后备。嵌入默认禁用；如启用，在 `.env` 自行加 `EMBEDDING_PROVIDER=openai_compatible`、`EMBEDDING_BASE_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_MODEL`，模型必须输出 **1536 维**。当前 `.env.example` 尚未列出这组嵌入变量，但运行时配置类支持。

别一开始无限循环。先跑一次 `run-once`，检查来源、Claim、Belief 和争议的数据库变化，再用 `run --max-cycles 5` 等有上限的命令。`status` 只有基础汇总，不是完整 30 天仪表盘。CLI 尚没有供用户直接输入问题并返回对话的命令。

## 8. 风险、优先级与可验收的下一步

### P0：让已有闭环可安全验收

1. 在专用 PostgreSQL/pgvector 测试库跑在线迁移、并发写入和向量召回；增加 0002 旧库、证据/争议并发、失败回滚与完整 `run-once` 场景。验收物是可复现日志和未丢失旧记录的证明，而不是仅有测试文件。
2. 给网页读取补 HTTP(S) 协议、DNS/IP 内网与回环地址、重定向最终地址、响应大小/类型的边界校验。现有读取器会跟随重定向并一次取得响应，长期无人值守前不应开放不受控 URL。保持搜索失败时能优雅降级。
3. 让主循环每个关键阶段可恢复，明确定义重复执行、部分写入和失败重试行为，并做故障注入测试；同时完善每日循环、搜索、令牌和费用预算。

### P1：证明“学会了”，而不是“看过了”

4. 把评估拆为出题、**不提供来源文本的闭卷回答**、独立来源核验、迁移题、保持测试和校准评分。保存题目、答案、来源和裁判身份；与当前模型自评作对照。
5. 增加来源血缘、内容质量和多段原文覆盖评估；对 Claim 支持关系建立可复核样本和误判率，不能只信单次模型裁决。
6. 接通争议调查队列：调查目标搜集双方证据，生成受现有门槛约束的决议提案，再调用 `DisputeResolver`；不允许新模型直接胜出。

### P2：长期学习与产品形态

7. 将 API、本地、网页模型调用统一记为等级 0 的 `ModelObservation`，由实际评估更新 `ModelProfile`；之后做模型迁移 A1/A2/B1/B2 对照。
8. 实现每日记忆整合、程序性技能提取和 Day 0/7/14/21/30 私有冻结基准。网页聊天界面、EXE 打包、服务器部署是**交互与交付方式**，不能代替这些可信度工作；若决定做，应单列产品需求和安全验收。

| BeliefHistory / 信念历史 | 谁在何时、因何证据改变了结论。 |
| pgvector | PostgreSQL 中存向量、检索相关信念的扩展；不是事实判定器。 |
| Alembic | 管理数据库结构随代码演进的迁移工具。 |
| 闭卷评估 | 回答时不让学习器看到刚读过的来源正文，再独立核对答案。 |
| 冻结基准 | 提前锁定、训练阶段不可见的测试题，用于比较长期能力变化。 |

---

**交接结论：** 项目最有价值的部分是“可追溯、可争辩、可长期保持的认知状态”，而不是模型或网页界面的数量。继续开发应先证明已有状态与测试可信，再增加自主程度和交互形式。
