# 项目分析与优化路线图

> 本文保留初始诊断与路线历史。Alembic、冲突晋升、目标重试、向量召回等早期问题已有后续实现；当前进度以[实现状态对照](实现状态对照.md)和[2026-10-02增量说明](20261002功能实施与使用说明.md)为准。

## 总体判断

Autodidact V0.1 的架构方向是正确的：它没有把某个 LLM 当成智能体本身，而是把目标、信念、证据、争议、评估和历史记录作为持久认知状态。当前代码已经贯通“目标选择、检索、综合、冲突检测、评估、信念晋升、生成跟进目标”的最小流程，适合作为概念验证版本。

不过，项目目前仍属于早期原型，而不是可长期无人值守运行的学习系统。主要原因不是缺少更多模型能力，而是数据迁移、事务一致性、证据独立性、闭卷评估和争议处理还没有形成可信闭环。

## 已具备的能力

- PostgreSQL/pgvector 数据模型已经覆盖目标、来源、主张、信念、证据、争议、历史、评估、技能和模型画像等核心对象。
- LLM 通过抽象类接入，主循环没有绑定具体模型。
- 搜索与网页读取失败会被捕获，单个外部来源失败不会立即中止整个循环。
- 新主张在信念晋升前会与已有信念比较，并在检测到矛盾时创建争议。
- 目标有显式状态机、确定性优先级评分以及前置目标和跟进目标生成机制。
- 自主循环没有暴露 shell、删除、自动登录、支付或权限提升能力。

## 当前关键风险

### 1. 数据演进没有迁移机制

`init-db` 仍使用 SQLAlchemy 的 `create_all`。它只能创建缺失对象，不能安全升级已有数据库。任何字段、约束、索引或枚举变化都可能让已有学习状态与新代码不兼容。

### 2. 矛盾主张仍可能直接晋升为新信念

主循环先创建争议，随后只要整体评估通过，就会把本轮所有主张继续晋升为信念。也就是说，同一条主张可能一边与旧信念形成争议，一边被创建为新的已验证信念。应为每条主张记录冲突状态，并阻止有未解决实质冲突的主张进入正常晋升路径。

### 3. “独立来源”目前只等同于不同来源 ID

已验证状态只依据 `source_ids` 去重后的数量判断。内容哈希可以发现完全相同的正文，却无法识别规范化 URL、转载、聚合页、同一机构或同一上游材料。因此两个网页并不必然代表两份独立证据。

### 4. 评估不是真正的闭卷评估

当前评估器同时看到学习结果和证据摘录，再由同一个 LLM 生成问题并评分。这更接近带材料的模型自评，容易产生信息泄漏和评分偏差，不能可靠证明智能体已经形成可迁移、可保持的知识。

### 5. 失败目标可能无限重试

目标选择会再次选取 `FAILED` 状态，而配置中的 `max_retry` 没有参与查询或状态转换。持续失败的高优先级目标可能长期占据队首，并阻塞其他目标。

### 6. 冲突检测的召回率和成本都会随数据增长恶化

每条新主张只与最近 40 条信念逐一进行 LLM 比较。它既可能漏掉较早但相关的信念，也会产生大量与主题无关的模型调用。已有的向量字段尚未用于候选召回。

### 7. 来源读取缺少网络边界防护

网页读取器会跟随重定向并读取搜索结果 URL，但目前没有显式限制协议、内网地址、回环地址、链接本地地址、响应体大小和重定向后的最终地址。长期自主运行前应补充 SSRF 与超大响应防护。

### 8. 模型观察和模型画像尚未进入运行链路

虽然已经有 `ModelObservation` 和 `ModelProfile` 数据表，但 API、本地和浏览器模型调用尚未统一落库，也没有依据真实评估结果更新模型画像。

### 9. 自动化测试覆盖面过低

现有测试只覆盖目标评分、一个 Pydantic 边界条件和浏览器模型配置构造。数据库事务、完整学习循环、提供方降级、争议、信念历史、去重和评估隔离都没有测试保护。

## 建议的实施顺序

### 阶段 0：恢复可重复的开发基线

1. 固化 Python 3.12 开发环境和依赖安装方式。
2. 在持续集成中运行 `pytest -q`、`python -m compileall -q src` 和 Ruff。
3. 添加最小数据库集成测试环境，并让一次模拟学习循环能够稳定重复运行。

完成标准：任何人从空白环境开始，都能用文档中的命令安装项目并得到一致的测试结果。

### 阶段 1：先保证持久状态正确

1. 引入 Alembic，生成与当前数据结构一致的基线迁移。
2. 为已有数据库提供安全的标记或升级说明，不删除已有学习数据。
3. 修复矛盾主张的晋升规则，并让争议历史记录真实保存信念原状态。
4. 落实 `max_retry`、退避时间、`BLOCKED` 状态和失败完成时间。
5. 为关键业务约束、外键、查询列和幂等操作添加约束与索引。
6. 将一次学习循环的重要数据库写入组织成明确的事务阶段，避免半完成状态难以恢复。

完成标准：进程在任一阶段中断后可以安全恢复；未解决的矛盾主张不会被标记为已验证；旧数据库可以无损升级。

### 阶段 2：建立稳定、安全的检索层

1. 定义 `SearchProvider` 协议和统一的搜索结果结构。
2. 接入至少一个稳定 API 提供方，将 DuckDuckGo HTML 作为后备。
3. 增加超时、有限重试、指数退避、熔断和提供方健康状态。
4. 规范化 URL，移除追踪参数，并按“规范化 URL + 内容哈希”去重。
5. 为网页读取增加协议、IP 地址、重定向、内容类型、响应大小和字符数限制。
6. 保存检索时间、最终 URL、发布者、发布时间和抓取元数据。

完成标准：主提供方失败时自动降级；重复或危险 URL 不进入证据库；同一上游材料不会被误算为多份独立证据。

### 阶段 3：让证据质量真正参与信念晋升

1. 建立确定性规则与模型辅助相结合的证据质量分类器。
2. 区分官方或第一手来源、同行评审资料、教材、二手资料、普通网页和模型输出。
3. 建立来源血缘与独立性分组，避免转载和同源引用重复计票。
4. 将证据等级、独立来源数、反方证据和主张覆盖度纳入晋升策略。
5. 对主张中的每个关键片段验证其引用 URL 确实存在于本轮来源中。

完成标准：`VERIFIED` 不再由网页数量决定，而由足够质量、足够独立且可追溯的证据决定。

### 阶段 4：实现可扩展的语义记忆与冲突召回

1. 定义 `EmbeddingProvider`，记录模型名称、维度和版本。
2. 为信念、主张和目标生成嵌入，并创建 pgvector 索引。
3. 采用“主题或关键词过滤 + 向量召回 + 重排”获取认识论上下文。
4. 冲突检测只比较语义相关的候选信念，并保留确定性预筛选与模型判断依据。
5. 设计嵌入模型变更时的后台重建与双版本兼容方案。

完成标准：知识规模增长后，相关旧信念仍能被召回；冲突比较调用量不再随全部信念线性增长。

### 阶段 5：建立真正独立的评估闭环

1. 将问题生成、闭卷回答、来源验证和评分拆成独立步骤。
2. 闭卷回答阶段不能看到来源正文或标准答案。
3. 优先使用确定性评分；需要模型裁判时，保存裁判模型身份并支持交叉裁判。
4. 冻结私有基准并按时间切分，避免学习数据污染评估集。
5. 增加保持测试、迁移测试、反例测试和置信度校准指标。

完成标准：能够分别报告基础模型得分、带记忆得分、记忆增益、保持度和校准误差。

### 阶段 6：接通模型观察、争议解决和模型迁移

1. 所有 API、本地和浏览器模型调用统一生成证据等级为 0 的 `ModelObservation`。
2. 用已验证结果更新 `ModelProfile` 的领域准确率、校准度和错误模式。
3. 实现 `DisputeResolver`，支持保留旧结论、采用新结论、条件化结论和保持未解决四类结果。
4. 所有信念变化都写入追加式 `BeliefHistory`，并关联所用证据和解析版本。
5. 实现 `ModelMigrationProtocol`，在相同冻结状态下比较新旧模型在有无记忆时的表现。

完成标准：更换模型不会静默改变知识；每次争议处理都可重放、可审计。

### 阶段 7：长期学习、可观测性与技能提取

1. 实现每日记忆整合、重复信念合并建议和过期知识复核。
2. 从多次成功与失败记录中提取程序性技能，并用独立任务验证后再提升置信度。
3. 增加 30 天指标、成本、延迟、提供方失败率、争议积压和知识老化指标。
4. 为完整学习循环、故障注入、数据库迁移和模型替换添加集成测试。

完成标准：系统可以解释自己学到了什么、依据是什么、保持了多久、在哪些领域真正提升，以及失败发生在哪里。

## 推荐的下一项开发任务

优先实现“阶段 1”的 Alembic 基线迁移与认识论一致性修复。它们是后续所有能力的地基：如果旧状态无法可靠升级，或矛盾主张仍能被直接晋升，那么更强的搜索、嵌入和模型只会更快地积累不可审计的数据。
