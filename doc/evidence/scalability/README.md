## 3. 关键词命中后仍做模糊回退

实际调用`HybridRetriever.retrieve`，关键词索引由替身预置1个命中；随后执行生产函数生成的模糊WHERE、排序与LIMIT，投影为ID，在内存SQLite执行。LIMIT为40、实际匹配1条。SQLite解释计划始终为`SCAN beliefs`和`USE TEMP B-TREE FOR ORDER BY`。

| N | 1词耗时ms / VM指令约数 | 8词耗时ms / VM指令约数 |
| ---: | ---: | ---: |
| 1,000 | 2.03 / 15,000 | 5.19 / 85,000 |
| 5,000 | 2.96 / 75,000 | 13.70 / 425,000 |
| 20,000 | 6.08 / 300,000 | 46.76 / 1,700,000 |

每次关键词已命中仍执行1次模糊回退。VM计数以1,000指令为粒度；它是SQLite工作量，不是实际行访问数、PostgreSQL执行计划或buffer量。此测量同时确认控制流中的无条件执行，以及一个内存关系引擎下的全表匹配成本；PostgreSQL必须另做EXPLAIN ANALYZE。

后续改动目标：对已完整建立索引的已命中记录避免回退，仅对明确缺索引数据或规定失败条件回退；新增回归保证旧记录可搜索，且所有分支仍复用P1接纳谓词。

## 4. 小批次索引重建的重复校验与同步

实际执行`RetrievalJobs.run`全部批次、`_verify`、摘要和1536维向量校验。存储和嵌入为内存替身；补齐候选/覆盖/物理索引查询为常量结果，故不含这些实库成本。同步计数来自`store.mark(row=...)`请求；真实store会调用`RetrievalIndex.sync`，本测量没有实际写数据库。

| 候选N | 每批B | 批次数 | 校验访问次数 | 重复关键词同步请求 | 同步请求合计 | 整个任务耗时ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 128 | 16 | 8 | 1,152 | 448 | 576 | 314.90 |
| 128 | 128 | 1 | 256 | 0 | 128 | 117.91 |
| 512 | 16 | 32 | 16,896 | 7,936 | 8,448 | 4,058.65 |
| 512 | 128 | 4 | 2,560 | 768 | 1,280 | 827.03 |

512项以16项小批处理时，关键词同步请求为新条目数的16.5倍；改为128项批次是2.5倍。前者总耗时约4.91倍，但单个最大锁区仍约453/457ms，不能用总时间下降推断最长锁占用同步下降。这里锁区只是业务临界区执行，未获取数据库锁，也未测并发等待。

N可整除B、全任务最终完成时，批次数K=N/B：校验访问为N×(K+1)，重复同步为B×K×(K−1)/2，新完成同步为N。实测断言逐场景核对；它说明固定小B时存在平方级累计重复工作。公式不涵盖失败重试、内容变化、populate/recover/覆盖SQL及状态聚合的额外实库成本。

后续改动目标：增量处理与全量验收分开，已完成且未变化项不重写关键词；最终启用仍要通过完整覆盖/指纹/摘要/向量/物理索引验证。不得为减少扫描跳过失效保护；最终验证和指针切换之间需保持并发一致性。

## 后续实施顺序与验收

建议先分离索引批次的全量重验，控制平方级累计重复；随后按风险逐项改全历史统计、去重身份键和模糊回退。这个顺序依据操作量与维护风险，并非已测出的生产收益排名。每次改动复跑相同场景并保存前后源码摘要，保持P1接纳回归和正式离线套件通过；真实PostgreSQL计划、事务/并发、实际锁等待、CPU/RSS/IO及召回质量属于下一阶段证据。
